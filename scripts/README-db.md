# Dual-engine database layer (`scripts/db.py`)

Every script in this repo opens its database through `scripts/db.py`, so
switching storage engines is a **configuration change, not a code change**.

## Selecting the engine

| `ZOLAI_DB_URL` | Engine | Driver |
|---|---|---|
| unset (default) | SQLite at the canonical core DB, `<workspace>/data/zolai.db` (override with `ZOLAI_DB_PATH` / `ZOLAI_DATA_ROOT`) | stdlib `sqlite3` (zero-dependency) |
| `sqlite:///path/to/db.sqlite3` | SQLite at an explicit path (relative = repo-root-anchored) | stdlib `sqlite3` |
| `postgresql://user:pass@host:5432/db` | PostgreSQL | `psycopg` (v3; psycopg2 auto-detected as fallback) |
| `postgres://user:pass@host:5432/db` | PostgreSQL (alias) | as above |

```bash
# local / offline (default — nothing to set up)
python3 scripts/dictionary/search_dictionary.py pasian

# against PostgreSQL
export ZOLAI_DB_URL='postgresql://zolai:secret@localhost:5432/zolai'
python3 scripts/dictionary/search_dictionary.py pasian
```

PostgreSQL needs the optional extra (SQLite needs nothing):

```bash
pip install "psycopg[binary]"
```

Resolution order for `connect(url=...)`:

1. an explicit URL containing `://` (a PostgreSQL URL always wins);
2. `ZOLAI_DB_URL` — this is what makes engine switching config-only;
3. `ZOLAI_DB_PATH` — canonical path override, same variable as `zolai-core`;
4. `ZOLAI_DATA_ROOT`/zolai.db, then the legacy `DATA`/zolai.db;
5. the bare path argument a script passes (sqlite) — anchored at the repo root,
   but redirected to the same-named file under the workspace `data/` dir when
   the repo-local copy is absent;
6. `<workspace>/data/zolai.db`, then `<repo root>/data/zolai.db`.

The canonical database is the ~2.9 GB / 132-table store beside this repo
(`../data/zolai.db`), owned by `zolai-core`. Scripts must not create a private,
empty `data/zolai.db`; `db_path()` returns the resolved core path, and
`data_root()` returns its parent directory for corpus files.

## Usage from a script

```python
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).resolve().parents[1]))
from db import connect, db_path, row_to_dict

DB_PATH = db_path()                    # canonical core DB, or env override
conn = connect(DB_PATH)                # honours ZOLAI_DB_URL first
cur = conn.execute("SELECT * FROM dictionary WHERE zolai = ?", ("pasian",))
row = cur.fetchone()
print(row_to_dict(row))
conn.close()
```

`connect()` is a drop-in replacement for `sqlite3.connect()`: same
`execute / executemany / commit / rollback / close / cursor / executescript`,
same cursor `fetchone / fetchall / rowcount / lastrowid`, and dict-like rows
on **both** engines (`row["col"]`, `row[0]`, and iteration all work). On SQLite
it also applies `PRAGMA journal_mode=WAL`, `busy_timeout`, and
`foreign_keys=ON`. PostgreSQL has no `lastrowid`; for INSERTs into tables with
an `id` column the cursor appends `RETURNING id` automatically, so
`cur.lastrowid` behaves the same on both engines.

## Portability rules (why both engines behave alike)

Scripts are written to a shared SQL subset so the same statement runs on either
engine. `connect()` translates `?` placeholders to `%s` on PostgreSQL
automatically, and `executescript()` / single `CREATE TABLE` calls go through
`translate_ddl()`: leading `--` comments are stripped (so a schema header cannot
hide a `PRAGMA`), `PRAGMA …` statements are dropped, and sqlite's
`AUTOINCREMENT` becomes `GENERATED BY DEFAULT AS IDENTITY`. That is the same
rewrite the Rust desktop layer applies (`zolai-tauri/src-tauri/src/db/mod.rs`).

- Placeholders are always written `?` — never `%s`, never f-string interpolation.
- Booleans are stored as `INTEGER` 0/1 (not `BOOLEAN`).
- Timestamps are ISO-8601 UTC strings (`2026-10-28T15:23:03Z`, `TEXT`);
  **never** `strftime()`, `datetime('now')`, or `CURRENT_TIMESTAMP` in SQL.
- JSON is stored as `TEXT` — no `jsonb` / `JSON1` dependency.
- Upserts use `INSERT … ON CONFLICT (cols) DO UPDATE SET …` (supported by both).
- Only `substr()`, `COALESCE`, and `SUM/COUNT` are used as SQL expressions.

## Known sqlite-only pockets

The connection layer is engine-neutral, but a few **schema/DDL maintenance**
scripts (`database/regenerate_db.py`, `database/clean_database.py`,
`online/migrate_schema.py`, `dictionary/build_dictionary_db.py`, and similar)
still contain `INSERT OR REPLACE/IGNORE`, `PRAGMA` **introspection**
(`PRAGMA table_info(…)` through `execute()`), or `sqlite_master` queries.
Every such file carries a `# sqlite-only` marker; list them with
`grep -rn '# sqlite-only' scripts`. These are not database *access* scripts, so
they never appear in the normal read/build path against PostgreSQL.
`AUTOINCREMENT` and script-level `PRAGMA` lines are already translated by
`executescript()`; the remaining pockets have no PostgreSQL equivalent without
knowing the conflict target or a catalog rewrite, so they run under the default
sqlite engine — on PostgreSQL, apply the schema out-of-band (Prisma) and keep
these scripts as sqlite tooling.
`scripts/bible/menu.sh` also embeds small interactive sqlite snippets and is
intentionally left as-is.

## Rebuild safety

A builder that `os.remove(DB_PATH)` + recreates the schema must never point at
the canonical store. Give it a sibling file and guard the delete:

```python
DB_PATH = db_path(name="dictionary/db/zvs_master_dictionary.db")
assert_rebuildable(DB_PATH, purpose="rebuild the dictionary builder DB")
```

`assert_rebuildable()` refuses to delete the core DB (or any file with 50+
tables) unless `ZOLAI_ALLOW_CORE_REBUILD=1` is set after a backup. This is why
the builders above no longer target `data/zolai.db`.

## Schema / migrations

`scripts/db.py` moves **data**, not schema. For managed schema evolution use
Prisma (`zolai-core/prisma/schema.prisma` is the schema of record) via
`prisma migrate`, or the dedicated migration scripts in `scripts/database/`.

## Core-database schema (canonical)

`data/zolai.db` (~2.9 GB, 132 tables) is owned by **zolai-core**. Dataset scripts
read and write it, but never define it. The headword tables are:

| Table | Key columns | Notes |
|---|---|---|
| `dictionary` | `zolai`, `english`, `english_clean`, `myanmar`, `pos`, `source`, `morph_features` | one row per headword; only `zolai` is NOT NULL |
| `dictionary_meanings` | `dictionary_id`, `zolai`, `meaning_en`, `example_zo`, `example_en`, `is_primary` | senses/examples, FK → `dictionary.id` |
| `dictionary_en_zo` | `headword`, `translations`, `pos`, `source` | English → Zolai reverse index |
| `vocabulary` | `headword`, `english`, `frequency`, `books`, `examples` | SRS columns (`ease_factor`, `interval`, …) live here |
| `zolai_vocabulary` | `zolai`, `root_word`, `tone_category`, `frequency_bible`/`_corpus`/`_songs` | richer sibling; **different columns** from `vocabulary` |
| `translations` | `source`, `target`, `direction`, `reference`, `confidence` | all five NOT NULL; **not** `(entry_id, translation)` |
| `canonical_sentences` | `text`, `tokens`, `pos_tags`, `grammar`, `source_hash`, `evidence_ids` | sentence-level POS gold |
| `bible_analysis` | `book`, `chapter`, `analysis_type`, `data` | document-level analysis |
| `bible_study_analysis` | `ref`, `book`, `chapter`, `verse`, `zo_text`, `en_text`, `my_text` | per-verse study notes |
| `tone_sandhi` | `rule_number`, `underlying_pattern`, `surface_pattern`, `condition` | **not** `zolai_tone_sandhi` |

The core DB contains duplicate-ish pairs (`proverbs`/`zolai_proverbs_idioms`,
`vocabulary`/`zolai_vocabulary`, `grammar_patterns`/`zolai_grammar_patterns`,
`bible_analysis`/`zolai_bible_analysis`) from historical merges. Both are
populated, so pick by column shape, not by name preference, and do not add a third.

### Column names scripts got wrong

The pre-merge dictionary schema used `headword` / `sources` / `raw_json`. In the
core store those are `zolai` / `source` / (spread across real columns, with
free-form extras in `morph_features` as JSON text). A script that still writes
the old names fails mid-loop, sometimes after earlier batches committed.

### Builders must not target the core DB

`build_dictionary_db.py` and `regenerate_db.py` create a private schema
(`entries`, `stems`, `fts_idx`) and **`os.remove()` their target first**. Pointed
at `data/zolai.db` that deletes the entire platform database. They now use
`db_path(name="dictionary/db/zvs_master_dictionary.db")` and call
`assert_rebuildable()` before deleting, which refuses the core path unless
`ZOLAI_ALLOW_CORE_REBUILD=1` is set.

## Auditing

`audit_core_schema.py` parses SQL literals out of every script and checks them
against the live schema — bad columns, missing tables, omitted NOT NULL columns,
and `CREATE TABLE`s that would add a table to the core store.

```bash
python3 scripts/audit_core_schema.py            # report
python3 scripts/audit_core_schema.py --strict    # exit 1 on errors (CI)
python3 scripts/audit_core_schema.py --json      # machine-readable
```

Scripts that own a scratch database are exempt: tables they `CREATE` themselves
are theirs, not core-schema violations.

## Portability

Timestamps are ISO-8601 strings written by Python
(`datetime.now(timezone.utc).isoformat()`), never `CURRENT_TIMESTAMP` /
`datetime('now')` / `strftime`, which emit the space-separated form that sorts
wrongly beside canonical rows. Placeholders stay `?`; `db.connect()` translates
them to `%s` for Postgres.
